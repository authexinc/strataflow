# 03 — Finish the stock Odoo restyle across every remaining inner page

The Strataline glass language reaches stock Odoo through three files and stops there: `static/scss/backend_variables.scss` (82 lines), `static/scss/backend_bootstrap.scss` (41 lines) and `static/src/stock/stock.scss` (83 lines). Those 83 lines cover the navbar, the control panel, buttons, dropdowns, modals, the form sheet, the list and a first pass at kanban. They do not cover the statusbar arrows, the notebook's active tab, the search panel, the search facets, empty states, the chatter's own bands, the Settings title bands, or anything specific to `account.move` and `crm.lead` — and six declarations that are already written are dead, beaten by a stock selector or a Bootstrap `!important` utility. A future session must turn "all inner pages" into the finite inventory below, land it in seven commits, and see every one of them in a browser. It matters because every path out of the six fullscreen screens — `+ New ticket`, `+ New invoice`, `+ New deal`, `Open in Odoo`, every smart button — lands the tenant on one of these pages, and a stock-looking page is the seam where the product stops looking like a product.

## What is true today

### The three seams, and what each may reference

Bundle order is fixed by `addons/web/__manifest__.py`. `web.assets_backend` (`web/__manifest__.py:49`) includes `web._assets_helpers` first (`web/__manifest__.py:50`), which is Bootstrap's `_functions.scss` / `_mixins.scss`, Odoo's `functions.scss`, `utils.scss`, then `web._assets_primary_variables` and `web._assets_secondary_variables` (`web/__manifest__.py:391-392`). Only then comes `web._assets_backend_helpers` (`web/__manifest__.py:51`), whose contents are `bootstrap_overridden.scss` and `bs_mixins_overrides_backend.scss` (`web/__manifest__.py:413-416`). Bootstrap's own `_variables.scss` is loaded *after* that, at `web/__manifest__.py:53`.

Consequences, both load-bearing:

- **`backend_variables.scss`** is prepended to `web._assets_primary_variables` (`strataflow_workorder/__manifest__.py:29-31`). It runs before `web/static/src/scss/primary_variables.scss` and every `*.variables.scss` (`web/__manifest__.py:376-379`), all of which declare `!default`. It may use Bootstrap *functions* and `o-to-rem` but no `$o-*` or `$gray-*` value, because none is defined yet. Its 82 lines already set the grey ramp, brand, surfaces, radii, navbar and the control-panel/kanban grounds.
- **`backend_bootstrap.scss`** is prepended to `web._assets_backend_helpers` (`strataflow_workorder/__manifest__.py:32-34`), so it runs before `bootstrap_overridden.scss` but *after* the primary variables. **It may reference `$o-*` variables; it may not reference Bootstrap's `$white`, `$gray-200`, `$border-radius` or `$body-color`, which are first declared by `bootstrap_overridden.scss` (`web/__manifest__.py:414`) immediately after it, and again by Bootstrap's own `_variables.scss` at `web/__manifest__.py:53`.** The existing 41 lines use only literals, which is why this has never bitten.
- **`stock.scss`** is swept into `web.assets_backend` by the glob at `strataflow_workorder/__manifest__.py:39`, so it lands after every `web`, `mail`, `crm` and `account` stylesheet. On a specificity *tie* it wins; on a specificity *loss* it does nothing at all.

`stock.scss:17` forces `@include tokens-light` on `.o_web_client`, so all stock pages are light regardless of the shell's toggle — locked in `ARCHITECTURE.md:37` ("Stock views … Strataline language, tenant-wide, light only") because `ir.http.color_scheme()` is hard-coded.

### Six declarations in stock.scss that do nothing today

These are not stylistic quibbles; they are rules the compiler emits and the browser discards.

1. **The toast is not glass.** `stock.scss:54` is `.o_notification { @include glass(var(--glass-80)); border-radius: 16px; box-shadow: var(--shadow-hi); }`. `web/static/src/core/notifications/notification.scss:15-17` is `.o_notification_manager { .o_notification { background-color: var(--Notification__background-color, #{$o-view-background-color}); } }` — specificity (0,2,0) against our (0,1,0), so the toast paints solid `#fbfcfa`. The template at `web/static/src/core/notifications/notification.xml:5` also carries `rounded shadow-lg`; Bootstrap utilities are emitted `!important` (`$enable-important-utilities` is on), so our `border-radius: 16px` and `box-shadow: var(--shadow-hi)` both lose too. What survives is the `backdrop-filter` and the border — a blur with nothing translucent behind it. The container is confirmed at `web/static/src/core/notifications/notification_container.js:12`.
2. **Kanban columns are not transparent.** `stock.scss:77` is `.o_kanban_view .o_kanban_group { background: transparent; }` (0,2,0). `web/static/src/views/kanban/kanban_controller.scss:206-208` is `.o_kanban_renderer.o_kanban_grouped .o_kanban_group { background: var(--KanbanGroup-background); }` (0,3,0) and wins. It is invisible today only because `backend_variables.scss:82` sets `$o-kanban-background: #f4f5f3`, which happens to equal `--bg`.
3. **`.o_kanban_view` is the wrong hook for anything variable-driven.** The class comes from `web/static/src/views/utils.js:47` (`o_${type}_view`) and sits on the view container. Every Kanban CSS variable is declared one level down on `.o_kanban_renderer` (`web/static/src/views/kanban/kanban_controller.scss:86-118`).
4. **The list `thead` rule fights a variable rather than setting it.** `stock.scss:72` paints `thead th` with `var(--logo-bg)`, but `--ListRenderer-thead-bg-color` (`web/static/src/views/list/list_renderer.scss:5`, default `$o-webclient-background-color`) is what paints the `th` at `list_renderer.scss:85` and is *also* read at `list_renderer.scss:105` (the sort icon inside a column header) and `list_renderer.scss:357` (`.o_list_actions_header`), which our rule never reaches, so those two spots stay `#f4f5f3` while the `th` is `#fbfcfa`.
5. **The group separator's weight and spacing are overridden.** `stock.scss:63` applies `@include eyebrow` (font-weight 800) plus `margin-bottom: 8px` to `.o_horizontal_separator`. `web/static/src/views/view_compiler.js:186` writes the class list as `o_horizontal_separator mt-4 mb-3 text-uppercase fw-bolder small`; `fw-bolder` and `mb-3` are `!important` utilities. Only the font-size, letter-spacing and colour from the mixin survive.
6. **`.o_form_statusbar { background: transparent }` at `stock.scss:60` is correct, but incomplete.** The stock rule it beats is `web/static/src/views/form/form_controller.scss:307-316`, which paints `$body-bg` when sticky at ≥md and `$o-view-background-color` inside a modal. Ours removes the paint entirely, so a sticky statusbar scrolls content underneath it. The stock rule exists for a reason.

## Decision needed

1. **The Odoo empty-state artwork.** `smiling_face.svg`, `neutral_face.svg` and `graph_background.png` (`web/static/src/views/view.scss:29,36,48`) are cartoon illustrations in Odoo's house style, and one of them is the first thing on an empty Invoices list (`account/views/account_move_views.xml:1982`). The two faces are `:before` pseudo-elements (`view.scss:25` and `:32`); `graph_background.png` is a background on `.o_empty_custom_dashboard` (`:43-49`), which only a custom dashboard renders. Options: (a) hide the two faces with `display: none` on their `:before` pseudo-elements and let the text carry the empty state; (b) commission Strataflow art and ship it in `static/description/`; (c) leave them. **Recommendation: (a).** It is one rule with two selectors, ships now, and the copy Odoo writes is already useful. (b) can be a later backlog item.
2. **A `<header>` on the ticket form.** Adding `<header><field name="status" widget="statusbar" clickable="1"/></header>` to `views/strataflow_workorder_views.xml`, between the `<form>` at `:25` and the `<sheet>` at `:26`, would give the new-ticket page the same statusbar every other Odoo form has, and it is the surface the statusbar work in this task exists to style. It is a change to *our* view, not a stock one. Risk: `status` transitions are guarded server-side by `action_advance` (`models/strataflow_workorder.py:109-113`, which raises `UserError` outside `NEXT_STEP`), so a clickable statusbar lets a user jump stages the button path forbids. **Recommendation: add the header with `clickable="0"`** — the shape and the visual language, none of the bypass.
3. **Kanban card gaps.** `web/static/src/views/kanban/kanban_record.scss:11` sets `margin: 0 0 (-$border-width)`, i.e. -1px, so cards butt together and collapse their borders. Our 16px radius plus `var(--shadow)` needs real gaps or the shadows clip. Setting `--KanbanRecord-margin-v` costs vertical density — roughly one fewer card visible per column. **Recommendation: take the gap.** A card with a clipped shadow reads as a rendering bug.

## Landmines

- **Sass eats CSS `min()` / `max()` with mixed units.** `min(52%, 460px)` compiles to `Incompatible units: 'px' and '%'` and kills the entire stylesheet bundle; Odoo then serves the **previous** CSS with only a small red banner at the foot of the page, so the change looks like a no-op rather than a failure. Grep every line you add for `min(` and `max(` before restarting. If you need one, spell it `Min(` / `Max(` — SCSS is case-sensitive and CSS is not, the trick Odoo itself uses at `mail/static/src/chatter/web_portal/chatter.scss:45-46`. Sizing is not a big part of this task, but step 5's kanban gaps are exactly where it would appear.
- **PREPEND, never append, in `_assets_primary_variables` and `_assets_backend_helpers`.** Odoo's and Bootstrap's declarations are `!default`; appended they land after ours and win. `strataflow_workorder/__manifest__.py:29-34` already uses `('prepend', …)`; do not change those tuples.
- **`backend_bootstrap.scss` may not reference Bootstrap variables.** It runs at `web/__manifest__.py:51`, before Bootstrap's `_variables.scss` at `:53`. `$white`, `$gray-200`, `$border-color`, `$body-color` do not exist yet. `$o-*` variables do (they come in at `web/__manifest__.py:391`). Step 2 uses literals for exactly this reason — a Sass "Undefined variable" here fails the whole bundle the same way `min()` does.
- **Odoo forbids `@import` between asset files.** Any file that wants the `glass`, `eyebrow` or `tokens-*` mixins must have `static/scss/tokens.scss` listed ahead of it in the same bundle. `strataflow_workorder/__manifest__.py:38` already does that for `web.assets_backend`; keep new SCSS inside `static/src/**` so the glob at `:39` picks it up after tokens.
- **Bootstrap utilities are `!important`; a rule can lose silently.** `$enable-important-utilities` is on, so `rounded-*`, `shadow-*`, `fw-*`, `m*-*`, `p*-*` and `text-*` all beat your rule regardless of specificity. Three declarations already in `stock.scss` die this way (see "What is true today"). Before writing a rule against a stock element, read its **template** for utility classes, not just its SCSS.
- **A stock selector with more classes beats you even though your file loads last.** `stock.scss` lands after every `web`/`mail`/`crm`/`account` sheet, so it wins ties — and only ties. `.o_notification_manager .o_notification` (0,2,0), `.o_kanban_renderer.o_kanban_grouped .o_kanban_group` (0,3,0) and `body:not(.o_touch_device) .o_settings_container …` (`web/static/src/webclient/settings_form_view/settings_form_view.scss:1`) are all higher than a one- or two-class rule.
- **Prefer setting an Odoo CSS variable over painting the element.** Most surfaces here (`--o-statusbar-*`, `--Notebook__link-*`, `--ListRenderer-*`, `--Kanban*`, `--settings__*`) declare their colour once as a custom property and then read it in three or four places. Painting one of those places leaves the others stock — that is exactly the `thead` bug in step 1.
- **Odoo's compiled CSS is not whitespace-minified.** Verify with regexes, never exact substrings.
- **Odoo CE has no dark mode.** `ir.http.color_scheme()` is hard-coded to `"light"`, `stock.scss:17` forces `tokens-light` on `.o_web_client`, and `holdPageGround` paints `<html>` in the *shell's* theme for 600 ms — so a light stock page flashes dark once after leaving a dark screen. Do not add `tokens-dark` anywhere in this task; dark stock views are their own backlog item (`BACKLOG.md:77-82`).
- **Quote grep globs in zsh.** `--include=*.xml` unquoted expands against the cwd and the flag silently vanishes.
- **"Verified server-side" is not verified.** Six visual bugs shipped past every HTTP check in a prior session and were caught in the first minute of actually looking. Every acceptance criterion below has to be seen in the automation tab.
- **New, found while reading this task:** the stock statusbar draws its arrow *border* as a second clipped `::before` filled with `--o-statusbar-border` (`web/static/src/views/fields/statusbar/statusbar_field.scss:69-90`). That variable defaults to `$o-view-background-color`, i.e. it is assumed to be **the colour behind the statusbar, not a border colour**. If step 1 and step 3 disagree about what the statusbar sits on, the arrow outlines paint a wrong-coloured halo rather than a hairline. The plan splits them across two commits, so between step 1 and step 3 the outlines are stock `$o-view-background-color` (`#fbfcfa`) over a `--bg` (`#f4f5f3`) statusbar; step 3 must set `--o-statusbar-border` to whatever step 1 left on `stock.scss:60`, and if either value changes later both change together.
- **New:** `web/static/src/views/kanban/kanban_record.scss:11` sets a deliberate `-1px` bottom margin so adjacent cards collapse their borders. Any radius or shadow on `.o_kanban_record` is clipped until that margin is cancelled — which is why `stock.scss:79` has looked wrong since it was written, and why step 5 must change the margin and the card in one go.
